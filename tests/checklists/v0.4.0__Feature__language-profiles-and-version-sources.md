**Target version:** 0.4.0

**Companion automated tests:** 31 new in 222 total -- `tests/test_repokit_config.py` (+6 functions, 17 cases: the vendored-copy skip, detection, the setting), `tests/test_sync_versions_sources.py` (8, new file), `tests/test_pre_commit_hook.py` (+1), `tests/test_pre_push_hook.py` (+3), `tests/test_update_common.py` (4, new file; real `git subtree` fixtures)

## What this is

The 0.4.0 release teaches repokit-common what language a project is written in and lets a project's version live somewhere other than a Python `_version.py`. The automated tests drive the hooks and tools in throwaway repositories under a temp folder, through git itself. What they cannot see is what this list is for: the hooks' output on a real console (code page, colour, wording), `update-common.sh` under Git for Windows' bash against a real subtree, what `dz git-snapshot` does when it is present, and what a real consumer sees after pulling 0.4.0. Anyone with git, Python 3.11+ and a shell can run it; nothing here touches a real repository unless a step says so.

## Prerequisites

1. git 2.30 or later with `git subtree` (Git for Windows ships it); Python 3.11+ on `PATH` as `python`; on Windows, Git's own bash (`C:\Program Files\Git\bin\bash.exe`), **not** WSL's.
2. A checkout of this repository at the 0.4.0 tree. Call its path `RK` below.
3. Everything below happens in a scratch folder. Make one and call it `SCRATCH`:

   **cmd.exe**
   ```cmd
   set SCRATCH=%TEMP%\rk-0.4.0-check
   mkdir %SCRATCH%
   ```
   **PowerShell**
   ```powershell
   $env:SCRATCH = "$env:TEMP\rk-0.4.0-check"
   New-Item -ItemType Directory -Force $env:SCRATCH | Out-Null
   ```
   **POSIX**
   ```bash
   export SCRATCH=/tmp/rk-0.4.0-check
   mkdir -p "$SCRATCH"
   ```
4. **Scratch-git rules.** Every git command below carries `-C <path>` so it can never land in a real repository, and every commit carries `-c user.email=t@example.invalid -c user.name=t -c commit.gpgsign=false -c tag.gpgsign=false`. On a machine with `commit.gpgsign = true` globally, a bare `git commit` opens a GPG dialog per commit. Never change global git config for this list. To keep the lines short, define once:

   **cmd.exe**
   ```cmd
   set G=git -c user.email=t@example.invalid -c user.name=t -c commit.gpgsign=false -c tag.gpgsign=false
   ```
   **PowerShell**
   ```powershell
   function g { git -c user.email=t@example.invalid -c user.name=t -c commit.gpgsign=false -c tag.gpgsign=false @args }
   ```
   **POSIX**
   ```bash
   g() { git -c user.email=t@example.invalid -c user.name=t -c commit.gpgsign=false -c tag.gpgsign=false "$@"; }
   ```
   Below, `g` means that command (`%G%` in cmd.exe).
5. **Reset between sections:** delete the section's folder under `SCRATCH` and start the section again. Nothing outside `SCRATCH` is written except where Section 7 says so (your own clone of this repository, read-only commands).

**Making a consumer.** Several sections need "a consumer": a scratch repository with this checkout vendored at `scripts/repokit-common/` and the hooks installed. The recipe, used as `make-consumer NAME`:

```
mkdir SCRATCH/NAME && g -C SCRATCH/NAME init -q -b main
copy RK's files into SCRATCH/NAME/scripts/repokit-common/   (everything except .git, private, tests/output, __pycache__)
g -C SCRATCH/NAME add -A && g -C SCRATCH/NAME commit -q -m seed
bash SCRATCH/NAME/scripts/repokit-common/install-hooks.sh     (from inside SCRATCH/NAME)
```
On Windows run the last line in Git's bash. A plain file copy is enough; Section 5 is the one place a real `git subtree` is needed and gives its own recipe.

## High-Value Verification (~5 minutes)

**If you only have 5 minutes**, run these five.

### HV.1 -- A Python project with no setting behaves exactly as before

Validates: AC2 -- zero change for the ~60 Python consumers.

- [ ] **Steps:** `make-consumer py`. Write `pyproject.toml` with `[project]\nname = "p"`, `mypkg/__init__.py` containing `import pdb`, and `tests/test_a.py` with one passing test. Add a bare remote: `g -C SCRATCH/py-remote.git init -q --bare -b main` and `g -C SCRATCH/py remote add origin SCRATCH/py-remote.git`. Commit, then `g -C SCRATCH/py push origin main`.
- [ ] **Expected:** the push is refused. The output shows `Product languages: python`, `ERROR: Debugger statements found (python)` and `Remove all pdb statements before pushing`. Remove the `import pdb` line, commit, push again: `[OK] Pre-push validation complete` (or the `✓` form on a colour terminal).
- [ ] **Why this matters:** if the default is anything but Python, every existing consumer's checks change on their next pull.

### HV.2 -- A TypeScript project gets its own checks and loses the Python warning

Validates: AC3.

- [ ] **Steps:** `make-consumer ts`. Write `.repokit-common.toml` containing `[tool.repokit-common]\nlanguages = ["typescript"]`, a `pyproject.toml` with `[project]\nname = "tooling"` (which used to trigger the Python package warning), `src/index.ts` with a line `debugger;`, and `tests/test_a.py` with one passing test. Add a bare remote as in HV.1; commit; push.
- [ ] **Expected:** refused with `Product languages: typescript` and `ERROR: Debugger statements found (typescript)`. No line `Warning: No Python package directory found`. Remove `debugger;`, commit, push: accepted.
- [ ] **Why this matters:** this is the first thing a non-Python consumer sees from the setting; the warning it removes taught people to ignore the hook.

### HV.3 -- A C header is bumped on its bytes

Validates: the C/C++ template's version source; AC-level "encodings preserved".

- [ ] **Steps:** `mkdir SCRATCH/hdr` and `g -C SCRATCH/hdr init -q -b main`; copy `RK/sync-versions.py` and `RK/repokit_config.py` into `SCRATCH/hdr/scripts/`. Write `.repokit-common.toml`:
  ```toml
  [tool.repokit-common]
  version-source = "include/demo/version.h"
  repo-url = "https://github.com/acme/demo"
  ```
  Write `include/demo/version.h` **with CRLF line endings and a UTF-8 BOM** (save it from an editor set that way, or run the Python one-liner below), containing:
  ```c
  #define DEMO_VERSION_MAJOR 0
  #define DEMO_VERSION_MINOR 1
  #define DEMO_VERSION_PATCH 0
  #define DEMO_VERSION_PHASE ""
  #define DEMO_VERSION_STRING "0.1.0"
  ```
  Python one-liner (any shell): `python -c "open('include/demo/version.h','wb').write(b'\xef\xbb\xbf' + '\r\n'.join(['#define DEMO_VERSION_MAJOR 0','#define DEMO_VERSION_MINOR 1','#define DEMO_VERSION_PATCH 0','#define DEMO_VERSION_PHASE \"\"','#define DEMO_VERSION_STRING \"0.1.0\"','']).encode())"` run from `SCRATCH/hdr`.
  Commit. Then from `SCRATCH/hdr`: `python scripts/sync-versions.py --bump minor`, then `python scripts/sync-versions.py --check`.
- [ ] **Expected:** `Bumping minor: 0.1.0 -> 0.2.0`; `--check` exits 0 (`All versions are in sync.`). Nothing is said about `__version__`.
- [ ] **Check:** `python -c "d=open('include/demo/version.h','rb').read(); print(d[:3]==b'\xef\xbb\xbf', d.count(b'\r\n'), b'MINOR 2' in d, b'\"0.2.0\"' in d)"` prints `True 5 True True`.
- [ ] **Why this matters:** a resource compiler reads this file; a lost BOM or changed line endings would show up as a build break in a C/C++ project, not here.

### HV.4 -- `versioning = "off"` makes commits quiet

Validates: the per-commit warning git-repokit has been printing goes away with one key.

- [ ] **Steps:** `make-consumer off`. Write `.repokit-common.toml` with `[tool.repokit-common]\nprivate-patterns = []`. Commit a file: note the output contains `Warning: Version update failed but continuing` (there is no version source). Now change the file to `[tool.repokit-common]\nprivate-patterns = []\nversioning = "off"` and commit again.
- [ ] **Expected:** the second commit's output has no line containing `Version` at all. `python scripts/repokit-common/sync-versions.py --check` prints `versioning is off for this project` and exits 0.
- [ ] **Why this matters:** a repository with no version source (notes, a tool versioned another way) should not nag on every commit.

### HV.5 -- `update-common.sh` pulls through the version stamp

Validates: AC6, the one visible behaviour change for consumers.

- [ ] **Steps:** follow Section 5.1 (it needs a real subtree, so it has its own recipe).
- [ ] **Expected:** the pull goes through with `Set aside the version stamp` and `Re-stamped mypkg/_version.py.` in the output, and the new upstream file arrives.
- [ ] **Why this matters:** before 0.4.0, nearly every consumer's tree was "dirty" by exactly this line and the pull refused; people worked around it by hand, sometimes losing the stamp.

## Section 1: `languages` -- the setting and detection (~10 min)

### 1.1 Detection from root markers, read with the tool

- [ ] **Steps:** in a scratch folder with `RK/repokit_config.py` copied into `scripts/`, create each of these in turn (empty files are enough) and run `python scripts/repokit_config.py --get languages --start scripts` after each: nothing; `pyproject.toml` containing only `[tool.repokit-common]`; `pyproject.toml` containing `[project]\nname = "p"`; `CMakeLists.txt`; `demo.vcxproj`; `Demo.csproj`; `package.json` (`{}`); `tsconfig.json` beside it.
- [ ] **Expected**, one per line: `python`; `python` (a tool-only pyproject is not a Python product, so the default applies); `python`; `python` plus `c-cpp` (two lines); then with the pyproject removed: `c-cpp`; `c-cpp`; `csharp`; `javascript`; `typescript` (tsconfig wins over package.json).
- [ ] **Check:** the output is one name per line, no quotes, no brackets.

### 1.2 The setting wins, and a bad value is named

- [ ] **Steps:** `pyproject.toml` with `[tool.repokit-common]\nlanguages = ["rust", "python"]`: `--get languages`. Then `languages = "python"` (a string): `--get languages`; note the exit code (`echo %ERRORLEVEL%` / `$LASTEXITCODE` / `echo $?`).
- [ ] **Expected:** `rust` then `python` on two lines (order kept, unknown names allowed). The string form prints `repokit-common: languages must be a list of names` on stderr and exits 2.

### 1.3 A C/C++ project runs no product checks

- [ ] **Steps:** `make-consumer cc`; write `CMakeLists.txt` (`project(demo)`), `tools/gen.py` containing `import pdb` and thirty `print(...)` lines, `tests/test_a.py` with one passing test; bare remote; commit; push.
- [ ] **Expected:** the push is accepted. Output has `Product languages: c-cpp`, `c-cpp: no product checks (the build and tests are the gate)`, `Python syntax check passed`, and no `Debugger statements` or `print() statements` lines.

### 1.4 Mixed languages run every profile

- [ ] **Steps:** in `cc`, set `.repokit-common.toml` to `languages = ["c-cpp", "python"]`; push again.
- [ ] **Expected:** `Product languages: c-cpp python`; the `import pdb` in `tools/gen.py` is now found (`Debugger statements found (python)`) and the push is refused.

### 1.5 An unknown language is said, not an error

- [ ] **Steps:** `languages = ["rust"]`; push.
- [ ] **Expected:** `rust: no product checks for this language yet`; the push proceeds.

### 1.6 Console rendering

- [ ] **Steps:** run HV.1's refused push once from a real terminal (not captured) and once captured (`> out.txt 2>&1`).
- [ ] **Expected:** the terminal run uses colour and `✗`/`✓` on a UTF-8 console; on a cmd.exe console in code page 437 or 1252 the markers must still be readable (no `?` boxes in place of `[X]`/`[OK]` -- the captured form always uses `[OK]`, `[!]`, `[X]`). Wording to judge: does `Remove all pdb statements before pushing` read clearly? Does `Product languages:` belong where it is (under the branch line)?

## Section 2: version sources (~10 min)

### 2.1 Plain `VERSION`: bump, phase, check

- [ ] **Steps:** a scratch repo with the two tools in `scripts/`, `.repokit-common.toml` with `version-source = "VERSION"` and `repo-url`, `VERSION` containing `0.3.6`. Commit. Run `--bump patch`, then `--phase alpha`, then `--check`, then `--phase stable`, then `--set 1.0.0 --force`.
- [ ] **Expected:** `VERSION` reads `0.3.7`, then `0.3.7-alpha`, `--check` exits 0, then `0.3.7`, then `1.0.0`. The file keeps a single line and its original line ending. No `__version__` output anywhere.

### 2.2 Header: `--set` with a phase writes every define

- [ ] **Steps:** in HV.3's repo: `python scripts/sync-versions.py --set 1.2.3 --phase beta --force`.
- [ ] **Expected:** the header shows `MAJOR 1`, `MINOR 2`, `PATCH 3`, `PHASE "beta"`, `STRING "1.2.3-beta"`; everything else byte-identical (re-run HV.3's check line: BOM `True`, CRLF count `5`).

### 2.3 Header with a non-UTF-8 byte

- [ ] **Steps:** add a comment line to the header with a cp1252 character, e.g. `/* édition */` saved in cp1252 (in Python: `b'/* \xe9dition */\r\n'`), then bump.
- [ ] **Expected:** the bump succeeds and the `\xe9` byte is still there (`b'\xe9dition' in open(...,'rb').read()` is `True`). The old text path would have failed to decode this file.

### 2.4 Python `_version.py` still stamps

- [ ] **Steps:** a scratch repo with `version-source = "mypkg/_version.py"` and the usual `MAJOR = ...`/`__version__ = "..."` file; `make-consumer`-style hooks installed; commit a change.
- [ ] **Expected:** the commit output has `Version updated for commit`; `__version__` carries `_main_<n>-<date>-<hash>`. Then `git -C ... log -1 --stat` shows `_version.py` in the commit. Unchanged from 0.3.x.

### 2.5 post-commit is quiet for a stampless source

- [ ] **Steps:** in the HV.3 (header) repo, install the hooks (`install-hooks.sh`) and commit a change.
- [ ] **Expected:** no `Version updated with commit hash` line after the commit (there is no hash to update), and no warning either.

### 2.6 A tool-less Python

- [ ] **Steps (optional, if a Python < 3.11 without `tomli` is at hand):** run `--check` in 2.1's repo with it.
- [ ] **Expected:** a warning that the settings file cannot be read without a TOML parser, then the placeholder default; the run does not crash.

## Section 5: `update-common.sh` -- the stamp-safe pull (~10 min)

Needs `git subtree` and, on Windows, Git's bash. Recipe for a real subtree consumer:

```
# upstream: a copy of RK's root files (update-common.sh, sync-versions.py, repokit_config.py, VERSION) in SCRATCH/up, one commit
g -C SCRATCH/up init -q -b main ; g -C SCRATCH/up add -A ; g -C SCRATCH/up commit -q -m "upstream v1"
# consumer
mkdir SCRATCH/con ; write pyproject.toml ([tool.repokit-common] version-source = "mypkg/_version.py"), mypkg/_version.py, .gitignore (__pycache__/)
g -C SCRATCH/con init -q -b main ; g -C SCRATCH/con add -A ; g -C SCRATCH/con commit -q -m consumer
g -C SCRATCH/con remote add repokit-common <absolute path of SCRATCH/up>
g -C SCRATCH/con subtree add --prefix=scripts/repokit-common repokit-common main --squash
# a second upstream commit to pull
write SCRATCH/up/NEW-FILE ; g -C SCRATCH/up add -A ; g -C SCRATCH/up commit -q -m "upstream v2"
```
`update-common.sh` adds the GitHub remote only when none named `repokit-common` exists; the scratch remote stops it reaching the network.

### 5.1 Only the stamp is dirty: snapshot, pull, re-stamp

- [ ] **Steps:** edit `mypkg/_version.py` changing **only** the `__version__ = "..."` line (as the pre-commit hook does). From `SCRATCH/con` run `bash scripts/repokit-common/update-common.sh`.
- [ ] **Expected:** either `Saved a dz git-snapshot of the tree.` (when `dz` is installed) or `Saved a copy of mypkg/_version.py at .../.git/repokit-common-stamp.bak.`; then `Set aside the version stamp in mypkg/_version.py (the only change); it is restored after the pull.`, the subtree pull output, `Re-stamped mypkg/_version.py.`, `Done.`; exit 0.
- [ ] **Check:** `scripts/repokit-common/NEW-FILE` exists; `mypkg/_version.py` has a `__version__` with the current branch, build count and hash (not the value you typed, and not HEAD's stale one); `git -C SCRATCH/con status --short` shows only `mypkg/_version.py` modified. With `dz`: `dz git-snapshot list` (run from `SCRATCH/con`) shows the snapshot.

### 5.2 Anything else dirty: refused by name, nothing touched

- [ ] **Steps:** reset the consumer (delete `SCRATCH/con` and redo the recipe, or `g -C SCRATCH/con reset -q --hard` on the scratch repo only). Dirty the stamp **and** write `mypkg/work.py`; stage it. Run the script.
- [ ] **Expected:** `Refusing to pull: the working tree has changes other than the version stamp:` followed by both files indented, `Commit or stash them, then run again. Nothing was touched.`; exit 1. `NEW-FILE` has not arrived; `git status --short` is exactly as before.

### 5.3 A real edit in the version file is work, not a stamp

- [ ] **Steps:** reset; change `MINOR = 1` to `MINOR = 2` in `_version.py` only; run the script.
- [ ] **Expected:** refused; the file still says `MINOR = 2`.

### 5.4 Clean tree pulls as before; `--check` still works

- [ ] **Steps:** reset; run the script with a clean tree; then `bash scripts/repokit-common/update-common.sh --check`.
- [ ] **Expected:** the plain pull with no `Saved`/`Set aside`/`Re-stamped` lines; `--check` prints local and upstream versions and `Up to date.`.
- [ ] **Why:** on Windows before 0.4.0 the prefix was computed as an absolute path and the pull failed with `was never added`; this is the regression check for the `git rev-parse --show-prefix` fix.

## What the automated tests DON'T cover

- Console rendering of the new hook lines (`Product languages:`, the profile-named errors) on cmd.exe code pages 437/1252 and on a colour terminal.
- `update-common.sh` under Git for Windows' bash in a real consumer with a GitHub remote (the tests use a scratch remote), and what `dz git-snapshot` records when it is installed (the tests accept either backup form).
- A real consumer pulling 0.4.0: claude-bookmarks (TypeScript, `.repokit-common.toml`) and a C/C++ project, then pushing through the new pre-push.
- A Python without a TOML parser (2.6).
- The wording and feel of the refusal messages and the `Set aside ... restored after the pull` sentence when read in the moment.
- Whether `tsconfig.json` beating `package.json` is the right rule for mixed JavaScript/TypeScript repositories (a design judgement; detection is overridable by the setting).

## Reporting issues found

1. Note the section and step number.
2. Capture the exact command and its full output (`> out.txt 2>&1`).
3. Keep the scratch repository that showed it (zip `SCRATCH/<name>`).
4. File an issue on DazzleTools/git-repokit-common referencing this checklist and the 0.4.0 commit.
